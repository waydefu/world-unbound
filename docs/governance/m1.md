# Governance M1 — minimum trusted quality gate

Status: **in progress.** Part 1 (this document's first version) adds base-policy re-validation, risk tiers, dependency review, exception checks and a cache ban. Part 2 adds lint. Negative-test evidence is collected after both parts merge.

AEGIS ∞ v2.0 chapter 16 defines M1 as: always-on gate, format/lint/type/unit, required integration, dependency scanning, CodeQL where available, stale-approval handling; acceptance T01/T02/T05/T06 plus the applicable T17/T20/T21/T26/T31/T33/T43/T44/T45.

## Platform limits found while designing M1

Checked against GitHub documentation on 2026-11-17:

- **`pull_request_target` is not a usable base-policy trigger here.** Its runs use the default branch's commit (`GITHUB_SHA`), the docs do not say its checks can satisfy a pull request's required check, and GitHub blocks it by default for public repositories from 2026-12-02.
- **Push rulesets ("Restrict file paths") are documented for private and internal repositories only**, so this public, personally owned repository cannot block edits to `.github/workflows/**` at push time.
- **Organisation "required workflows" do not apply to a personal account.**

Consequence: **no GitHub-native mechanism here stops a pull request from deliberately editing its own CI so that it passes.** M1 therefore catches accidental weakening automatically, makes deliberate weakening require a visible edit to `.github/workflows/`, and records the remaining risk instead of claiming it is solved.

## Controls

| Control | Mechanism | Stage |
| --- | --- | --- |
| Always-on gate | `final-gate` runs on every event and rejects failed, cancelled, skipped or missing jobs | Enforce (required) |
| Types, unit tests, build, static audit | `app-checks` | Enforce |
| Headless render and resilience sweep | `visual-audit` | Enforce |
| Dependency review | `dependency-review`: blocks new dependencies with high or critical advisories, or licences outside the allow-list (MIT, Apache-2.0, BSD-2/3-Clause, ISC, 0BSD, MPL-2.0, CC0-1.0, Unlicense, BlueOak-1.0.0, Python-2.0, CC-BY-4.0) | Enforce |
| Base-policy re-validation | `base-policy`: runs the **base commit's** validator against the pull request | **Warn** (not required) |
| Risk tier | `base-policy` job summary: R0–R3 from the **base commit's** `sensitive-paths.yml`, with R3 escalations for install scripts, registries, workflow write permissions and privileged containers | Warn (report only) |
| Governance exceptions | `policy-syntax`: schema, unique ids, self-approval ban, review dates; an expired exception fails only when the change touches its scope | Enforce |
| No caches | Validator rejects `actions/cache` and `cache:` inputs in every workflow | Enforce |
| Pinned actions, no privileged triggers, no `secrets: inherit`, no blanket permissions | Validator | Enforce |
| CodeQL (JavaScript/TypeScript, Actions) | GitHub default setup, run by GitHub rather than by this repository's workflows | Enforce if the owner adds "Require code scanning results" to the ruleset |
| Lint | Part 2 | — |

**Why base-policy starts at Warn.** A pull request that intentionally changes the gate (like the one introducing it) fails the rules as they stand on main, so making it required would block every governance change unless the owner temporarily edits the ruleset. AEGIS D03 prescribes Shadow → Warn → Enforce. Promotion to required is an owner decision once its false-positive rate is known; if promoted, governance changes need a recorded break-glass ruleset edit (`docs/runbooks/break-glass.md`).

## Acceptance matrix

| Test | Scenario | Status |
| --- | --- | --- |
| T01 | PR removes required workflows or lowers policy | **Partly met.** Accidental weakening of validator rules is caught by `base-policy` (warn). Deliberate edits to `.github/workflows/` cannot be blocked on this platform; they rely on the owner reviewing the diff. **Unmet as a technical control.** |
| T02 | Forged status with the same name | **Partly met.** The ruleset requires `final-gate` from the GitHub Actions app, so external statuses cannot satisfy it; a job in an edited workflow can still use the name (see T01). |
| T05 | Required job skipped but reported as success | Met — gate self-test with skipped, cancelled, neutral, failure and missing cases. |
| T06 | Stale approval reused | Not applicable while required approvals are 0; dismiss-stale is enabled for when approvals are required. |
| T17 | Fork PR poisons a cache used by a release | Met by design — no caches in any workflow, enforced by the validator. |
| T20 | Fork PR gets basic CI without secrets | Met by design (no workflow uses secrets; `pull_request` gives forks a read-only token). **Not exercised** — needs a fork from a second account. |
| T21 | Fork reaches policy secrets in a second stage | Not applicable — there is no second stage and no secret. |
| T26 | AI-stated "pass" overrides a failing CI | Met — merge requires `final-gate`, which reads job results, never PR text. |
| T31 | Registry, build script, install script or workflow permission change escalates to R3 | Met — unit tests; reported, not blocked. |
| T32 | Benign lockfile update is not R3 | Met — unit test (R2). |
| T33 | Lockfile and manifest disagree | Met — `npm ci` fails; evidence to collect. |
| T36 / T37 | Expired exception blocks its scope only | Met — unit tests. |
| T43 | Privileged workflow runs a local action from the PR | Met — privileged triggers and local actions are rejected by the validator. |
| T44 | Reusable workflow inherits all secrets | Met — `secrets: inherit` rejected. |
| T45 | GitHub API rate limit | Fail-closed: dependency review and label sync fail on API errors rather than passing. Graceful degradation for non-core checks is not implemented. |
